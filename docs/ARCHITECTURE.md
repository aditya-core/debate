## 2. The one thing I'd push back on: Django on Vercel

Vercel is a **serverless** platform. Every function is request-scoped: it boots, answers, dies. Django is a **long-lived process** framework — that mismatch produces five concrete problems, none of which are stylistic:

| # | Constraint (Vercel) | What it does to Django |
|---|---------------------|------------------------|
| 1 | Request/response body max **4.5 MB**, not configurable | Audio uploads and large payloads fail at the platform layer with `413` *before your code runs* |
| 2 | Hobby functions time out at **10s**; Pro default 15s, max 300s | An AI evaluation call (Gemini + speech scoring) routinely exceeds this. You cannot do it inside the request |
| 3 | **No persistent WebSocket connections** | Rules out Django Channels — no live speaking-room, no streaming feedback, no realtime turn-taking |
| 4 | No background workers, no `celery worker`, no `manage.py` process | Evaluation jobs, transcripts, XP recalculation and emails have nowhere to run |
| 5 | Deployment size + cold starts | Django + psycopg + celery + google-genai easily blows the bundle budget and starts cold in ~1–2s |

Django *can* be forced onto Vercel through the Python runtime. It is a demo, not a home.

### Recommendation: split the two runtimes

```
┌─────────────────────────┐       ┌──────────────────────────┐
│  Next.js (web)          │       │  Django (api)            │
│  Vercel                 │──────▶│  Railway / Render / Fly   │
│  • landing page, motion │ fetch │  • DRF, business logic    │
│  • dashboards           │ JWT   │  • Supabase JWT check     │
│  • auth session (SSR)   │       │  • Celery workers         │
└─────────────────────────┘       └────────────┬─────────────┘
           │                                   │
           │ @supabase/ssr                     │ psycopg
           ▼                                   ▼
┌──────────────────────────────────────────────────────────────┐
│  Supabase  —  Postgres (Mumbai) · Auth · Storage · Realtime  │
└──────────────────────────────────────────────────────────────┘
                    │
                    ▼
        ┌──────────────────────────┐
        │ Redis  — Celery broker,  │
        │ rate limits, cache       │
        └──────────────────────────┘
```

**Why not drop Django entirely and go "pure Supabase"?**
It's a legitimate option and the simplest one — but you lose: a real ORM with migrations, the Django admin (genuinely useful for content, rubrics and support), server-side Python for AI orchestration, and a place to put complex domain logic without fighting Row Level Security. If you *know* Django, keeping it is worth the extra deploy target. If Django were only a "maybe", I'd say drop it. Your call.

**Cost of the split:** one extra deploy target, one extra CI job, ~$5–10/month. Acceptable.

## 4. Auth flow with Supabase + Django (the caveat)

**Supabase is the identity provider. Django is a resource server. Django never sees a password.**

```
Signup (browser) ──▶ Supabase Auth ──▶ JWT (ES256, short-lived + refresh)
                          │
                          │ webhook / first request
                          ▼
                    Django: get_or_create Account by supabase_uid
                          │
                          ▼
              Account + DebateProfile + ExtemporeProfile  (D-004)
```

- Django verifies the token against Supabase's JWKS (`/auth/v1/.well-known/jwks.json`), caching keys; no shared secret, no per-request round trip.
- Django maps `sub` → `Account.supabase_uid` (unique, indexed). The `GOW-*` display IDs are generated **inside** that creation step, in one transaction.
- **⚠️ The caveat:** Row Level Security in Supabase only protects requests that arrive *through PostgREST with a user's token*. Django connects as a superuser/`service_role` and **bypasses RLS entirely**. So:
  - Do **not** design authorisation as "RLS will handle it".
  - Authorisation lives in Django, once, in querysets and permissions.
  - Use RLS only if the browser ever talks to Supabase directly (e.g. Storage). For Storage, use signed URLs issued by Django instead.
- **Never** expose the `service_role` key to the browser. Ever.

## 5. Data model sketch (identity first, because everything hangs off it)

```python
class Account(models.Model):            # GOW-USER-XXXXX  (display)
    id            = UUIDField(primary_key=True)      # real key
    supabase_uid  = UUIDField(unique=True, db_index=True)
    display_id    = CharField(unique=True)           # GOW-USER-7K4M2QW
    email         = EmailField()
    date_of_birth = DateField(null=True)             # drives age gate
    country       = CharField(max_length=2)
    created_at, updated_at
    # billing fields land in Stage 8, not now

class DebateProfile(models.Model):      # GOW-DEB-XXXXX
    account      = OneToOne(Account, related_name="debate")
    display_id   = CharField(unique=True)
    rating       = DecimalField(default=1000)        # independent
    xp           = PositiveIntegerField(default=0)   # independent
    created_at

class ExtemporeProfile(models.Model):   # GOW-EXT-XXXXX
    ... same shape, independent rating/xp
```

Three rules that keep the "two worlds" design honest:

1. **No shared rating column.** Ever. If Debate and Extempore need the same numbers, they compute them separately.
2. **Sessions belong to a world profile**, not to the Account. `DebateSession.debate_profile`, `ExtemporeSession.extempore_profile`.
3. **The shared intelligence layer is read-only.** It runs as an aggregate/analytics module that queries across both and writes only to `DevelopmentInsight`, never back into ratings.

XP and rating as **append-only events** (`RatingEvent`, `XPEvent`) with the current value denormalised onto the profile. Reason: you will want to re-score, audit, and show "why did my rating change" — a single mutable integer makes all three impossible.

## 6. Motion + performance: the ₹15k-phone rulebook

Motion is a **must** (D-009). So the engineering goal is not "less motion" — it is **motion that costs nothing**.

### Device tiers — decided at boot, before any heavy work

| Tier | Signals | Experience |
|------|---------|-----------|
| **3 — Low** (most ₹15k phones, 2–3 GB RAM, older Android WebView) | `deviceMemory ≤ 3`, `hardwareConcurrency ≤ 4`, `effectiveType` `2g/3g`, `saveData`, or a 3-frame timing probe over budget | Static poster + CSS/SVG motion only. No canvas. Hero visual = pre-rendered loop |
| **2 — Mid** | `deviceMemory 4–6`, decent GPU string, ≥30fps probe | WebGL at `dpr ≤ 1`, ≤ 6k particles, no post-processing (no bloom/DoF), 30fps cap, reduced ribbon segments |
| **1 — High** (desktop, flagship phones) | 8 GB+, discrete/strong GPU, probe ≥55fps | Full R3F scene, bloom, parallax, full particle count, 60fps |

Probe honestly: render 3 cheap frames with `requestAnimationFrame` and measure. Do not trust user-agent sniffing; Safari has no `deviceMemory`.

### Hard budgets

- **Hero path JS ≤ 180 KB gzip** before interaction. `three` is ~150 KB alone — so it is **never** in the initial bundle. It is dynamically imported after first paint, on tiers 1–2 only.
- LCP element = the **H1 text**, not the canvas. Font preloaded, `font-display: swap`, no CLS from late-loading type.
- Animate **`transform` and `opacity` only**. Never `top/left/width/height/filter` in a loop.
- One `IntersectionObserver`, one `rAF` loop for the whole page — not one per component.
- Pause the canvas when off-screen or when the tab is hidden.
- `prefers-reduced-motion: reduce` → the entrance story is replaced by the end state; no particle scene, no scroll-jacking.
- WebGL unavailable → poster image + CSS shimmer. The page must still feel designed, not broken.

### The mobile "looks cheap" trap

A shrunken desktop 3D scene is the fastest way to look amateur. Tier 3/2 phones get a **pre-rendered** ribbon loop (WebM VP9, ~720p, ~400 KB, or a 120 KB poster with a slow CSS gradient drift). Rendered properly, it looks *better* than a janky real-time scene at 18fps — and it is the honest engineering answer to "motion graphics is a must, on a ₹15k phone".

## 7. Speech evaluation — the seam we build now, decide later

Deferred by decision, but three things must exist regardless:

1. **A `Scorer` interface** in `api/apps/evaluation/`: `score(audio_ref, prompt, rubric) -> ScoreResult`. Gemini is one adapter; a dedicated pronunciation/fluency engine is another. Swapping must not touch the domain.
2. **Store the rubric version and model name with every score.** Feedback you cannot reproduce is feedback you cannot debug, appeal or improve.
3. **Audio never travels through the API server.** Browser → Supabase Storage (signed upload URL issued by Django) → Django enqueues a Celery job → worker fetches, transcribes, scores, writes `ScoreResult`. This sidesteps the 4.5 MB limit, the request timeout, and keeps the request fast.

## 8. Legal & compliance baseline (build it in, not bolt it on)

India-first, global-ready. The product targets teenagers — this is not optional paperwork.

| Requirement | What it means concretely |
|-------------|--------------------------|
| **DPDP Act 2023 — children** | Under-18s need **verifiable parental consent**. Age gate at signup → parent email verification → recorded consent artefact (who, when, version of notice). No behavioural tracking or targeted ads at children. |
| **DPDP — notice & purpose** | Plain-language consent notice, purpose-specific, itemised. Not a 40-page policy dressed as consent. |
| **DPDP — data principal rights** | Access, correction, erasure. Build "download my data" and "delete my account" before launch, not after. Erasure must cascade to audio files in Storage. |
| **DPDP — breach** | Documented 72-hour notification path to the Data Protection Board + users. |
| **Voice = sensitive** | Separate, explicit, revocable **recording consent**, distinct from ToS acceptance. Show retention window (e.g. raw audio deleted 30 days after scoring; transcript retained). |
| **Grievance officer** | Named person + email on the site. Required. |
| **GDPR/UK GDPR** (if EU/UK reach) | Lawful basis per purpose, DPA with Supabase/Vercel/Google as processors, SCCs for transfer, DSAR within 30 days. |
| **AI transparency** | Every AI-generated score labelled as AI. (EU AI Act direction + simple trust.) |
| **Sub-processor page** | Supabase, Vercel, Google (Gemini), email provider, monitoring. Public list. |
| **Data residency** | Supabase project in **Mumbai (`ap-south-1`)**. Cheap now, impossible to change later. |
| **Docs to exist before launch** | Privacy Policy · Terms of Service · Cookie Policy · Acceptable Use · Voice Consent · Security contact (`security.txt`) |

Two of these — the age gate and the erasure cascade — are **schema decisions**, not legal pages. They have to be in the first version of the data model or we migrate later.

## 9. What's still missing from the stack (the "anything else?" list)

| # | Missing piece | Why it matters | Proposal |
|---|---------------|----------------|----------|
| 1 | **Background job queue** | AI scoring, transcription, emails, XP recalculation — none can run in a request | Redis + Celery (worker + beat) |

| 10 | **Testing floor** | Not a religion, just a floor | pytest for domain logic (rating, XP, ID generation), Playwright for the hero + signup journey |

### 11.2 The uncomfortable finding

Django + Celery on a **free** host has exactly one good answer — a self-managed Oracle VM — and that answer requires Aditya to be a sysadmin on top of being a founder.

Meanwhile **Next.js + Supabase alone needs no third service at all**, has no cold start, and — the important part — **the RLS caveat (R-010) evaporates.** With no Django holding a superuser connection, the browser's JWT *is* the only path to the database, so RLS becomes real security rather than decoration.

That is not a budget compromise dressed up as architecture. It is a simpler, genuinely coherent design for this product's shape.

## 12. Capacity plan: can 100 users launch on free tier?

**Answer: yes — with four build conditions, all of which are engineering decisions we control.** Worked out below with the real shape of this product (100 users × ~3 practice sessions/week, 2-minute recordings, text feedback).

### 12.1 The budget at 100 users

Assumptions: 2-minute recording ≈ 360 KB (Opus/WebM), session transcript + AI feedback ≈ 15 KB, ~40 API calls per user-day.

| Resource | Estimated use at 100 users | Free limit | Headroom |
|----------|---------------------------|-----------|----------|
| Supabase — database | 15–25 MB/month | 500 MB | ~20–30 months |
| Supabase — storage | ~20 MB (in-flight audio only) | 1 GB | **50×** |
| Supabase — egress | 0.5–1 GB/month | 5 GB | 5–10× |
| Supabase — auth MAU | 100 | 50,000 | 500× |
| Vercel — function invocations | ~180,000/month | 1,000,000 | 5× |
| Vercel — data transfer | ~3 GB/month | 100 GB | 30× |
| Vercel — **active CPU** | ~1.5–4 hours/month | **4 hours** | ⚠️ **tight — the real ceiling** |
| Gemini — requests | ~300/day | ~1,500/day | 5× |
| Gemini — requests/minute | peaks of 5–10 | ~15 RPM | ⚠️ tight during a simultaneous class |

### 12.2 The four launch conditions

Without these, free tier does not hold. With them, 100 users is comfortable.

**1. Custom SMTP from day one — this is the actual launch blocker.**
Supabase's built-in email sender is capped at **2 emails per hour** and **only delivers to members of your Supabase organisation**; any other address is rejected with `email_address_not_authorized`. A real user cannot even confirm their signup. Fix: Resend (free, 3,000/month) as custom SMTP, then raise the limit under Authentication → Rate Limits.

**2. Delete the raw audio after scoring.**
1 GB ÷ 360 KB ≈ 2,800 recordings. At 100 users that is ~10 weeks of audio — then the app breaks. With deletion after scoring, storage holds only in-flight clips (~20 MB). Required by DPDP anyway (D-023). Legal and budget demand the same thing.

**3. The landing page is static (or ISR), never server-rendered per request.**
The 4-hour active-CPU budget is the thin margin. A static landing page costs ~0 CPU; an SSR one with a WebGL-heavy page can burn the monthly budget in a week of traffic.

**4. A pinger and a weekly backup.**
`cron-job.org` / UptimeRobot free hitting a DB read every few hours defeats the 7-day pause. `pg_dump` to a private bucket weekly defeats "no backups on free". Both are ~15 minutes of setup and both are unrecoverable mistakes if skipped.

### 12.3 Where 100 users is *not* enough

Be clear about the ceiling so it is never a surprise:

- **100 concurrent** heavy practice sessions — no. 100 total users with 5–10 online at once — yes.
- **Monetisation** — Vercel Hobby forbids commercial use. Free beta, no payments, no ads: defensible. First paying user: Vercel Pro ($20).
- **Beyond ~500 users** — storage and Gemini daily requests become the binding constraints before anything else.
- **No SLA, no automatic backups, no support** — you are accepting that risk explicitly, and mitigating 2 of the 3 yourself (§12.2 item 4).

### 12.4 The AI data caveat

Gemini's free tier and paid tier have different data-use terms. Before sending **minors' voice recordings and transcripts** to a free-tier API, that difference must be read properly — it is a DPDP question, not a cost question. If the free tier permits training on submitted data, Phase 0 must not process real students' audio through it. **Verify before Stage 5, not after.**

### 12.5 Verdict

**D-031:** Keep the stack. Target: launch-ready product for **100 users at ₹0/month**, with §12.2 as non-negotiable build conditions and §12.3 as the documented ceiling. Upgrade triggers: first payment taken → Vercel Pro; 7-day pause or storage pressure → Supabase Pro; both ≈ **$45/month**.
